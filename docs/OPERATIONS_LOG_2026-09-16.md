## 메모리 상한을 넘으면 무슨 일이 일어나는가

**포드는 죽지 않는다. Forge 프로세스 하나가 죽는다.**

OOM 시 희생 순위 (실측):

```
score=704  rss=14.2GB  Forge (launch.py)      ← 1순위
score=666  rss= 0.2GB  jupyter-lab
score=666  rss= 0.1GB  code-server
PID 1      score=666   docker-init            ← 컨테이너 본체, 메모리 거의 안 씀
```

컨테이너는 09-11 기동 이후 무중단인데 그 사이 Forge는 13번 죽었다. GPU 할당도
그대로 유지됐다. 잃는 것은 **진행 중이던 배치의 대기열**이지 포드나 GPU가 아니다.

단, `dmesg`가 컨테이너에서 차단돼 있어 OOM killer 기록을 직접 확인하지는 못했다.
사인은 정황 증거(상한 도달, 파이썬 예외 없는 즉사, 진행률 도중 로그 단절)에
기반한 추정이다. 반면 "컨테이너는 살아남는다"는 5일간의 실측이다.

## 장애 이력과 원인

### 1. 이미지 혼합 업로드

여러 프로젝트 이미지가 한 zip에 섞여 올라갔다. 인덱스 범위만 보고 잘랐기 때문이다.

**대응**: `finish_project.py`에 `--start-idx`/`--end-idx`/`detect` 추가.
이후 `finish_multiday.py`는 인덱스가 아니라 **PNG 메타데이터의 `<lora:...>`로
걸러낸다.**

### 2. Gradio 고착 (09-15)

`RuntimeError: deque mutated during iteration`으로 Forge가 살아는 있으나 응답만
하는 상태가 됐다. 당시 리스너는 PID 존재 여부만 봐서 감지하지 못했다.

**대응**: 리스너를 3단 헬스체크로 재작성 (PID → API 응답 → interrupted 고착).

### 3. 6시간 배치 사망 (09-16 04:01)

리코 배치가 83/100에서 끊겼다. 6시간 5분 연속 가동 중 메모리 상한에 도달했다.

이때 `preventive_restart.py`(5시간마다 예방 재시작)가 있었다면 막혔을 것이라고
보고했으나 **틀렸다.** 이 스크립트는 작업이 돌고 있으면 무기한 미룬다:

```python
if job != "":
    log("restart due but job in progress - deferring")
    exit(0)
```

6시간짜리 단일 작업 도중이었으므로 한 건도 막지 못했을 것이다.

또한 이 포드에는 `bootstrap_pod.sh`가 실행된 적이 없어(`bootstrap.log` 부재,
crontab 비어 있음, 스크립트 부재) **cron 자동화가 애초에 설치돼 있지 않았다.**
"3중 복구 레이어"라고 설명했던 것은 저장소 코드를 보고 한 말이지 포드 상태를
확인하고 한 말이 아니었다. 실제로는 리스너 1중이었다.

### 4. 배치 중단을 완료로 오판

Forge가 재시작되면 대기열이 사라져 작업이 비므로 정상 완료와 구분되지 않는다.
83/100에서 끊긴 리코 배치를 완료로 보고 미완성본 656장을 업로드했다.

**대응**: 배치 중 `restart_count`가 늘었는지로 판별해 `batch_aborted`로 노출.
`auto_finish_watcher.py`는 중단이면 업로드하지 않고 경보만 남긴다.

### 5. 고착 감지 오탐 — 멀쩡한 Forge를 죽임 (09-16 16:04)

`interrupted && 작업 없음`이 15초 지속되면 재시작하도록 만들었는데, 이 조건은
고장 신호가 아니었다. 설정에서 **Reload UI를 누르거나 생성을 수동 중단해도**
`interrupted`가 남고 다음 작업까지 해제되지 않는다.

```
16:04:29  Forge UI 정상 재시작 (Restarting UI, 기동 3.9초)
16:04:45  리스너가 고착으로 오판 → 멀쩡한 Forge 강제 종료
```

**대응**: 진짜 고착은 로그에 아무것도 기록하지 못한다는 점을 이용해
`forge_log_active()` 추가(최근 180초 내 로그 기록 시 제외), 임계값 15초 → 10분.

같은 조건이 16:31에 재발했을 때 재시작하지 않고 걸러낸 것이 로그로 확인됐다.

### 6. UTC 자정을 넘는 배치

Forge는 자정에 새 날짜 폴더를 만들고 인덱스를 0부터 다시 시작한다. 날짜 폴더
하나만 받는 `finish_project.py`로는 자정 이후 생성분이 통째로 누락된다.

**대응**: `finish_multiday.py` — `--spec 날짜:시작[:끝]`을 여러 번 받는다.
테리 배치에서 실제로 09-16분 613장 + 09-17분 192장을 합쳐 805장을 정확히 묶었다.

### 7. 세션 간 조율 부재

## 미해결 / 주의

1. **메모리 상한은 근본 해결되지 않았다.** 긴 배치 *도중* 상한에 닿는 것을 막는
   장치는 없고, 있어서도 안 된다(작업을 죽이게 되므로). 실질적 대책은
   **배치를 잘게 쪼개는 것**이다. 100배치를 25배치씩 4회로 나누면 손실 위험도
   4분의 1이 된다.
2. **WebUI 무한 로딩** — 서버 측 지표는 전부 정상이고 잘못된 응답이 한 건도
   없었다. 루트 페이지가 5.8MB(`gradio_api_info` 4MB + `gradio_config` 1.9MB)로
   무겁다는 점은 확인했으나 근본 원인은 미확정. `show_api=False`로 줄이려 했으나
   Gradio 4.39는 이 설정과 무관하게 인라인해 효과가 없었고 원복했다.
   nginx 진단 로그(`/var/log/nginx/diag.log`)를 켜둔 상태.
3. **`/workspace` 밖은 컨테이너 재생성 시 소실된다.** crontab, `/root/.config/rclone`,
   `/etc/nginx/nginx.conf`가 여기 해당한다. 컨테이너가 새로 만들어지면
   `bootstrap_pod.sh`를 반드시 한 번 실행해야 한다.
4. `bootstrap_pod.sh`는 리스너를 crontab에 등록하지 않는다. 현재 포드에는 수동으로
   `@reboot /workspace/listener/start.sh`를 추가해 뒀다.

## 절대 규칙

- **포드를 정지시키지 말 것.** RTX 4080 SUPER는 RunPod에 매물이 없어 한 번 내리면
  같은 GPU로 복구할 수 없다. 메모리 상한 초과와는 다른 층위의 문제다.
- `rclone.conf`는 구글 드라이브 전체 접근 권한이다. 공개 저장소
  (`castle923/AutoRunpod`)에 절대 커밋하지 않는다. 비공개 `Runpod-Backup`의
  `secrets/`에만 둔다.
